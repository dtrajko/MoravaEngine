The short version

Today MoravaEngine is a renderer with a scene editor around it: one executable that loads .mscene files and draws them very well. A game engine adds three things on top of that. Behavior: the scene must change by itself over time, driven by physics, scripts, input and sound. A play/edit separation: the editor runs the game on a copy of the scene and throws the copy away when you press Stop. Shipping: a second, small executable (the player) that runs one game from cooked files, without the editor, the importers or the shader compiler.

The phases are ordered so that each one ends with something that runs. Phases 1 to 4 make the first playable game (a ball rolled with the keyboard that collects pickups). Phases 5 to 7 add what a real small game needs (sound, characters, menus). Phases 8 and 9 make it shippable: cooked assets in one pack file, and a Build Game window that writes a folder you can zip and send.

Theory primer

The game loop and the fixed time step

Rendering runs as fast as the screen allows, and the frame time varies. Simulation must not depend on it: a physics step of 33 ms behaves differently from two steps of 16.7 ms (objects tunnel through walls, jumps get higher). The standard answer (Glenn Fiedler, Fix Your Timestep) is an accumulator: each frame adds the real elapsed time, and the simulation runs whole fixed steps (for example 1/60 s) while enough time has accumulated. The remainder, as a fraction of a step, is the interpolation factor: the renderer draws each moving body between its previous and current simulated position, so motion is smooth even when 60 Hz simulation meets a 144 Hz screen.

Two kinds of game code follow from this. Fixed update runs once per simulation step: forces, character movement, anything physics sees. Update runs once per rendered frame: cameras, animation parameters, UI.

Entities, components and systems

The scene already is an ECS: entities are IDs, components are plain data, EnTT stores them. What is new is systems: functions that run every frame over all entities with certain components (all rigid bodies, all sound sources, all scripts). A system may keep runtime handles in a component (the Jolt body ID, the managed object handle, the miniaudio sound). Those are never saved and never copied into a new scene; the system creates them when Play starts.

What a physics engine does

Each step: the broad phase finds pairs of bodies whose bounding boxes overlap (Jolt uses a tree per broad-phase layer, for example one for static and one for moving bodies), the narrow phase computes exact contacts for those pairs, and the solver applies impulses so bodies don't sink into each other and respect joints. Object layers decide who collides with whom (the player with walls, but bullets not with other bullets). A sensor (trigger) reports overlaps but pushes nothing. A character controller is not a rigid body: it is a shape moved by code that slides along walls, climbs steps and stands on slopes, because a rolling capsule feels wrong for a player.

Hosting .NET in a C++ program

.NET is normally started by dotnet.exe or an app's own executable. A game engine instead hosts it: the engine loads hostfxr (the .NET host resolver), tells it which runtime to use (a .runtimeconfig.json), and asks for a native function pointer to a static C# method. From then on, C++ calls C# through that pointer. For calls the other way, C++ passes a table of its own function pointers to C# at startup, and C# calls them through delegate* unmanaged fields. Both directions are plain function calls with blittable arguments (numbers, structs of numbers, pointers): no marshaling layer, very fast. C# methods called from C++ are marked [UnmanagedCallersOnly].

Sound in 3D

An audio engine mixes many sources into the output for one listener. For a 3D source it computes, from the listener's position and orientation, a volume (distance attenuation between a minimum and maximum distance) and a stereo pan, optionally a pitch shift for moving sources (Doppler). Buses (groups) let the player turn music and effects up and down separately. Short sounds are decoded into memory; music is streamed from the file.

Source assets and cooked assets

Editors work with source assets: .fbx, .png, .glsl, flexible and slow to load. Games ship cooked assets: the same data converted once into the form the GPU and the runtime want (vertex buffers as bytes, block-compressed textures, compiled SPIR-V), so loading is a file read and an upload. Cooking also decides what ships: only assets reachable from the game's scenes.

The design rules

  1. The core knows nothing about the editor. No ImGui, no ImGuizmo, no assimp, no shaderc in MoravaCore once Phase 8 is done. The editor adds panels and tools around it; the player adds a window and nothing else.
  2. The scene is the game state. Physics, audio and scripts read and write components. They keep only runtime handles of their own, and these are rebuilt from components when Play starts.
  3. Play happens on a copy. Nothing a running game does can change the scene you are editing.
  4. Everything a game ships with is referenced by UUID and cooked. No path relative to the working directory survives into the player.
  5. Each phase is proven by a small game, not only by a test scene: roll-a-ball after Phase 4, a third-person collector after Phase 7, the exported collector after Phase 9.
  6. Debug views stay. As in the rendering work, each phase's views (colliders, input values, sound ranges, UI rectangles) remain in the editor for learning and debugging.

What the plan avoids

  • A second scripting language. Lua would be easy to add later through the same component, but C# alone keeps the engine basic.
  • Visual scripting, networking, terrain editing, a material graph. Not needed for basic games.
  • OpenGL and DirectX 11 in the player. The player is Vulkan only (MoltenVK on macOS). The legacy scenes stay in the editor executable as samples.
  • Interim fixes. When a later phase solves something properly (asset paths in Phase 8, for example), earlier phases don't add a temporary workaround; they name the phase.

1.1 Take the scene and the UI out of the renderer

This is the largest step of the phase and must come first, because the player can't link a renderer that draws editor panels. Split EnvMapVulkanRenderer.cpp along three lines:

  • The editor in src/Editor (Editor, EditorSelection; one file per panel: EditorViewport, EditorHierarchyPanel, EditorPropertiesPanel, EditorLightsPanel, EditorEnvironmentPanel, EditorMaterialPanels, EditorStatsPanel, with EditorDocument, EditorClipboard, EditorSceneEdits, and what they share in EditorState.h), without graphics API code; the older OpenGL editor classes moved to src/Editor_Legacy. Its windows are built through SetUserInterface, called while the renderer records the window's image. Aligning the sun to a newly loaded map is the editor's: it watches GetEnvironmentVersion.
  • Limit: the scene and its components live in src/EnvMapVulkan and name the Vulkan material class, so src/Editor is compiled only in builds with Vulkan (CMake says so). An API-neutral scene needs the material data separated from the GPU material: a task of its own.
  • Found on the way: the sun's "follow the environment rotation" remembered the rotation across scene loads, so opening a scene could turn its sun by the difference to the previous scene's rotation; it now starts over with each scene. And the probes' final state depends on their first frames (they stop updating once nothing changes, and the bounces build on earlier values), so a frame's difference in when a scene's probe volume first appears changes the converged GI slightly.

1.3 The player

The player is an Application with one layer, PlayerLayer (proposed), that loads the project, opens the start scene, runs the game loop and renders. Two things differ from the editor:

  • Presenting: the viewport composite goes to the swapchain through a final full-screen pass, instead of being sampled by the ImGui Viewport panel. The camera's aspect ratio follows the window.
  • The working directory: the engine loads files relative to the current directory (MoravaEngine/ in development). The player sets the current directory to its own folder at startup. Phase 8 replaces paths with UUIDs, so this stays the only path rule.
As built: the player shows a scene
  • Files. src/Player: PlayerMain.cpp (only main), PlayerApplication (the ApplicationClient: the renderer, one layer, Draw) and PlayerLayer. MoravaPlayer --scene <file.mscene> opens the scene with EnvMapVulkanSceneLoader::Open and hands it to the renderer with its render settings and no view options: the defaults are a game's view (no grid, selection, overlays or debug view). Since projects (1.6), --project gives the start scene; --scene stays, for tests.
  • The camera. Every frame the camera is put where the scene's camera entity is, with its field of view: EnvMapVulkanSceneData::PlaceCamera, now shared with the editor's SyncCamera (the same math, moved). A scene without a camera entity is seen from the origin, with a warning. The viewport size is the swapchain's every frame, so the aspect ratio follows the window.
  • Presenting. A new pass, Present.glsl, copies the viewport composite (exposed, tonemapped, with bloom) to the swapchain image. It replaced the old SceneComposite quad there, which tonemapped the raw scene again without bloom. In the editor that quad was hidden under the panels, so the editor looks the same (same captures); in the player it is the whole window.
  • Failing clearly. No --scene, or a file that can't be opened: the reason in the log and exit code 1, so a test can tell. Application::Close(exitCode) sets the code main returns.
  • CI. The player runs GI_Cube.mscene for 20 s after the editor's smoke test, on Linux (lavapipe) and macOS (MoltenVK), with the same checks: crash, hang, exit code, validation messages, files not found. Windows runners have no GPU, so Windows only builds the player.
  • Not yet: the working directory. Changing to the player's own folder only matters when the data sits next to the executable, which first happens in an exported game (Phase 9). It is done there, where it can be tested; until then the player starts from MoravaEngine/, as the editor.

1.4 The game loop

// GameLoop.cpp (proposed), called once per frame in Play
void GameLoop::Frame(float frameTime)
{
    frameTime = std::min(frameTime, 0.25f);          // after a breakpoint or a hitch: no "spiral of death"
    m_Accumulator += frameTime * m_TimeScale;        // TimeScale 0 = paused game, UI still runs

    while (m_Accumulator >= FixedStep)               // FixedStep = 1.0f / 60.0f
    {
        m_Scripts.FixedUpdate(FixedStep);             // Phase 4
        m_Physics.Step(FixedStep);                    // Phase 3: also stores previous/current transforms
        m_Physics.DispatchEvents(m_Scripts);          // contacts and triggers, on the main thread
        m_Accumulator -= FixedStep;
    }
    m_Alpha = m_Accumulator / FixedStep;              // for interpolated rendering

    m_Scripts.Update(frameTime * m_TimeScale);
    m_Animation.Update(frameTime * m_TimeScale);      // Phase 6
    m_Audio.Update(m_Scene);                          // Phase 5: listener and source positions
    m_Scene.FlushDeferred();                          // destroyed entities, scene loads requested by scripts
}

The existing Timer keeps giving the frame time; its update-rate logic is not used by the game loop. Until Phase 3 the loop only has the frame update, but its shape is final.

As built: the game loop
  • Files. src/Game/GameLoop.h/.cpp, in the core: Frame(frameTime) with FixedStep (1/60 s), MaxFrameTime (0.25 s), the time scale (0 or more), the alpha, Reset for the next start, and counters: frames, fixed steps, game time. Comments in Frame mark where scripts, physics, animation, audio and the deferred scene changes go; until then the loop only keeps time.
  • The player runs it. PlayerLayer::OnUpdate calls Frame first, then places the camera where the game put the camera entity. At exit it logs the counters: GI_Cube.mscene for 20 s gave 5198 frames, 1185 fixed steps, 19.76 s of game time (19.76 × 60 = 1185.6: the steps follow game time, not the frame rate). The editor runs it in Play (1.5).
  • The frame time. Not from Timer after all: it is ticked only in the older scene class's Update, which the player doesn't have, so the player's layers got 0 every frame. Application::Run now measures each frame with steady_clock and gives it to the layers' OnUpdate. The editor's first frame no longer gets the startup time (several seconds) as its frame time; otherwise it is the same. Timer stays for the older scenes.

1.5 Play, Pause, Step, Stop

EnvMapVulkanScene forbids copying today, on purpose. Add an explicit CopyFrom(const EnvMapVulkanScene&) that copies every component in a list of component types, keeping entity IDs (so the editor's selection still points at the same entity during Play). The same type list later drives prefabs and the script API.

// EnvMapVulkanComponents.h: one list of the components that are scene data
using AllComponents = ComponentList<IDComponent, NameComponent, HierarchyComponent, TransformComponent,
    ModelComponent, MeshPartComponent, SunComponent, PointLightComponent, SpotLightComponent, WaterComponent,
    ProbeVolumeComponent, CameraComponent, EnvironmentComponent /* Phase 3+: RigidBody..., Script..., AudioSource... */>;

void EnvMapVulkanScene::CopyFrom(const EnvMapVulkanScene& other)
{
    Clear();
    for (EnvMapVulkanEntityID id : other.AllEntitiesInHierarchyOrder())
        CreateEntityHandle(id);                       // same ID, no components yet
    AllComponents::ForEach([&](auto tag) {
        using T = typename decltype(tag)::Type;
        other.m_Registry.view<const T>().each([&](entt::entity e, const T& c) {
            m_Registry.emplace_or_replace<T>(Handle(other.IdOf(e)), c);   // runtime handles are reset by each type's copy
        });
    });
    m_Roots = other.m_Roots;
}
Models are shared, not reloaded ModelComponent::Model is a RefH2M: the copy shares the loaded model, so Play starts instantly. That is safe while the game only moves entities. If a script ever edits mesh data, it must clone the model first.

The toolbar's controls, as in Unity (the Play button becomes Stop while the game runs):

  • Play: the editor scene is copied, the copy runs, the view comes from the scene's camera.
  • Pause: the game loop stops, the scene stays as it is: look around, select, inspect.
  • Step: while paused, exactly one frame (one variable update and the fixed steps it is due), then paused again. For watching a collision or a script bug frame by frame.
  • Stop: the copy is destroyed, the edited scene is shown again, unchanged.
  • Simulate (Phase 3, 3.7): Play without scripts and with the editor camera. It comes with Jolt: before it, there is nothing for it to run.
As built: Play, Pause, Step, Stop
  • The copy. EnvMapVulkanScene::CopyFrom creates the entities in the hierarchy's order with their IDs, then copies each type of SceneComponents (EnvMapVulkanComponents.h: every component but IDComponent, which the scene gives each entity; a new component must be added there). The scene's self-test checks a copy: same entities, IDs, hierarchy and components, and changes to it don't reach the original.
  • Which scene runs. The game runs on the editor's scene, the one every panel and the renderer show, and the edited scene waits in a copy that comes back at Stop. It is the same as running a copy (nothing the game does reaches the edited scene), but no panel had to learn about a second scene: the Hierarchy and Properties show and edit the running game.
  • What else is kept. The render settings, and the matrices of the models' meshes: the models are shared, and a part's transform is written into its mesh. At Stop, the editor's own state about the scene starts over: the environment rotation the sun follows (else the sun would be turned back with an environment the game turned), and what the probes gathered from the game's scene (OnSceneReplaced).
  • The check. At Play the scene is saved as text, at Stop the scene that came back is compared with it, and the log says the edited scene is back, unchanged, or an error. A scene whose models and environment were moved during Play comes back unchanged and looks as before Play, up to the GI's noise (the probes settle to a slightly different noise after their reset, ±1 brightness level).
  • The view. While the game runs: the camera is placed where the scene's camera entity is (as in the player), the camera entity no longer follows the editor's camera, and the viewport is the game's (no camera flying, picking, gizmo, light icons, grid or selection outline; Delete and Ctrl+C/V do nothing there), framed in blue. Paused: the viewport is the editor's again (fly, select, inspect), framed in amber; going on puts the view back on the camera entity. Stop puts the camera back where it was at Play.
  • Step runs one frame of exactly one fixed step (GameLoop::Frame(FixedStep)), whatever the editor's frame time: Step after Step gives the same steps. The frame counter goes up by one per Step.
  • Not while the game runs: Save, Save As, New and Open (a notification says to Stop first), and removing a part of a model (its mesh would leave the model the edited scene shares). The unsaved-changes check pauses. Material Library edits are not scene data and stay after Stop, as asset edits in Unity.
  • Files. Editor/EditorPlayMode.cpp: the state, Play and Stop, the game loop, the toolbar (Play/Stop, Pause, Step centered in a taller menu bar, drawn icons, then the frame and the game time) and the viewport's frame. The Hazel stubs of EnvMapVulkanEditorLayer stay unused. Ctrl+P plays and stops, as in Unity; the screenshot it took in the older Scene class moved to F12.
  • Unattended. --play starts the game once the scene given with --scene is open; with --exit-after the game is stopped at exit, with the check. The editor's smoke test in CI runs with it and requires the check's line.

Input is sampled once per frame into a snapshot (GLFW keys and mouse, glfwGetGamepadState for every connected gamepad; GLFW ships the SDL gamepad mapping database). Edges need care: a key pressed and released between two fixed steps must still be seen by OnFixedUpdate. Keep "pressed since the last fixed step" flags that are cleared after each fixed step, separate from the per-frame flags that OnUpdate sees.

struct ActionState
{
    glm::vec2 Value = {};          // Button: x = 0 or 1

Two settings to decide on purpose
  • Defines must match. Jolt checks at startup that the library and the program were compiled with the same JPH_* defines (double precision, debug renderer, ...). Linking the Jolt target PUBLIC takes care of it; don't add JPH_* defines by hand.
  • CPU instruction sets. Jolt's CMake turns on modern x64 instruction sets (AVX2 and others) by default. A shipped game must run on the customer's CPU: check the USE_* options of the pinned version and choose a baseline (for example SSE4.2 + AVX) deliberately. On Apple Silicon it uses NEON.

3.4 Components

struct RigidBodyComponent
{

    float Mass = 1.0f;
    float LinearDamping = 0.05f, AngularDamping = 0.05f;

    uint32_t Layer = ObjectLayers::Dynamic;

struct ColliderComponent                       // one per entity; a body collects colliders of its entity and children
{
    enum class Shape { Box, Sphere, Capsule, ConvexMesh, TriangleMesh } Type = Shape::Box;
    glm::vec3 Offset = {}, HalfExtents = glm::vec3(0.5f);
    float Radius = 0.5f, HalfHeight = 0.5f;
    float Friction = 0.5f, Restitution = 0.0f;
    bool IsTrigger = false;                    // JPH: mIsSensor
};
  • Scale: the entity's world scale is baked into the shape when Play starts (ScaledShape). Spheres and capsules accept only uniform scale; the Inspector warns otherwise.
  • Mesh colliders: built from a MeshPartComponent's vertices. Triangle meshes only for static bodies; moving bodies use a convex hull or simple shapes.
  • Hierarchy: a dynamic body simulates in world space. After each step its world transform is written back with SetWorldTransform, so a body under a moving parent still behaves physically. Static bodies under a moving parent are a mistake the panel points out.
  • Interpolation: Step stores the previous and current world transform of every dynamic body; the renderer draws mix/slerp by the loop's alpha. Kinematic bodies move with MoveKinematic(target, dt), so they push dynamic bodies correctly.
As built: bodies in the Vulkan scene (3.3, 3.4)

  • Components, slightly changed from the proposal.   • Shapes and scale. The entity's world scale is baked into the shape at Play: box half extents and offsets scale per axis, a sphere takes the largest scale, a capsule the larger of X and Z for its radius (the panel warns about non-uniform scale). 3.6 Events and queries

Contact callbacks run on Jolt's worker threads ContactListener::OnContactAdded and OnContactRemoved are called from inside Update, on several threads at once. Never call scripts or touch the scene there: push {bodyA, bodyB, kind} into a mutex-protected queue and dispatch it on the main thread after the step. OnContactRemoved gets only sub-shape IDs, so keep a set of active pairs to report the right entities.

Queries for scripts: Raycast (closest hit: entity, point, normal, distance) through GetNarrowPhaseQuery().CastRay, ShapeCast for sphere sweeps, Overlap for "what is in this box". Each takes a layer mask.

Debug views: Physics
  • Colliders: every shape as lines, colored by state (static gray, active green, sleeping blue, trigger yellow), drawn into the viewport through DebugRendererSimple.
  • Contacts: contact points and normals of the last step.
  • Physics panel: body counts by type, step time, active pairs, the collision matrix editor.
As built: events, queries and debug views (3.6)
  • Events. A JPH::ContactListener (ScenePhysicsContactListener) only writes down, behind a mutex, which pairs of bodies gained or lost a contact; after the step ScenePhysics turns that into events on the main thread. Jolt reports contacts per pair of sub-shapes (a mesh touches with each of its triangles), so a pair of bodies keeps a count: from none to some is an Enter, from some to none an Exit, whatever order the threads reported them in. GetEvents() gives the last step's events (CollisionEnter/Exit, TriggerEnter/Exit: the entity, the other one, where they first touched and the normal), for the scripts of Phase 4; trigger events are also logged. A character is reported with its inner body: when it enters a trigger, and when a dynamic body bumps into it.
  • Triggers. A trigger without a moving rigid body is made kinematic and never sleeps, with mCollideKinematicVsNonDynamic: Jolt's static sensors lose a body when it falls asleep (a character standing still in a zone would "leave" it), and only a kinematic sensor senses kinematic bodies such as a character's inner body. Checked unattended: a character standing in a trigger for 21 s gets one Enter and no Exit; a ball rolling through gets one of each.
  • Queries. Raycast (the closest hit: entity, point, surface normal, distance), SphereCast, OverlapSphere and OverlapBox, each with a mask of layers (ObjectLayers::Solid by default: everything but triggers) and, for the casts, an entity to go through (the one asking). A character's inner body counts as the character.
  • The collision matrix. PhysicsCollisionMatrix: the four layers (Static, Dynamic, Character, Trigger) and which pairs collide, a project setting written in the .mproject file as Physics: {Collisions: [Static-Dynamic, ...]} and passed to the world at Play. Static with Static and Trigger with Trigger can't be turned on. Layers of the game's own (Player, Enemy, Projectile) come when scripts need them.
  • Debug views and the Physics panel (View > Physics). Colliders draws every shape as lines over the viewport (static gray, awake green, sleeping blue, trigger yellow, character orange), where the picture has the bodies (between their last two steps). The shapes are walked by the engine instead of Jolt's DebugRendererSimple, which exists only in Jolt's Debug and Release builds and draws a sphere as hundreds of triangles: boxes as 12 edges, spheres and capsules as circles, hulls as their faces, meshes as their triangles (5,000 at most). Without Play the scene's Box, Sphere and Capsule colliders and the characters show from their components, so Fit to Model can be checked while editing. Contacts draws the last step's contact points with their normals (the characters' too). The panel shows the bodies by type, how many are awake, the touching pairs, the step times, the last 100 events, a query test from the view's center (ray, sphere cast or overlap, drawn in magenta), and the collision matrix. The lines are ImGui's, like the light gizmos: not depth tested, so a collider is seen through a wall. With both views on, the Physics scene drops from about 20 to 14 frames per second in the Debug editor; they are off by default.

4.1 Start with a spike

4.2 Starting the runtime

// ScriptHost.cpp (proposed). nethost.h, hostfxr.h, coreclr_delegates.h come from the .NET SDK's
// Microsoft.NETCore.App.Host.<rid> pack (static nethost library + headers); char_t is wchar_t on Windows.
bool ScriptHost::Init(const std::filesystem::path& dotnetRoot, const std::filesystem::path& scriptCoreDll)
{
    get_hostfxr_parameters params { sizeof(params), nullptr, dotnetRoot.c_str() };   // private runtime folder
    char_t buffer[1024]; size_t size = std::size(buffer);
    if (get_hostfxr_path(buffer, &size, &params) != 0) return false;
    LoadHostfxrExports(buffer);       // LoadLibrary / dlopen + hostfxr_initialize_for_runtime_config, _get_runtime_delegate, _close

    hostfxr_initialize_parameters init { sizeof(init), nullptr, dotnetRoot.c_str() };
    hostfxr_handle context = nullptr;
    auto config = scriptCoreDll; config.replace_extension(".runtimeconfig.json");
    if (m_Init(config.c_str(), &init, &context) != 0) return false;

    load_assembly_and_get_function_pointer_fn loadAssembly = nullptr;
    m_GetDelegate(context, hdt_load_assembly_and_get_function_pointer, (void**)&loadAssembly);
    m_Close(context);

    using InitFn = int (CORECLR_DELEGATE_CALLTYPE*)(const NativeApi*, ManagedApi*);
    InitFn initialize = nullptr;
    loadAssembly(scriptCoreDll.c_str(), STR("Morava.Interop, Morava.ScriptCore"), STR("Initialize"),
                 UNMANAGEDCALLERSONLY_METHOD, nullptr, (void**)&initialize);
    return initialize(&s_NativeApi, &m_Managed) == 0;   // hands over C++ functions, receives C# ones
}

struct ManagedApi
{

    void (*InvokeFixedUpdate)(void* instance, float dt);

// Morava.ScriptCore/Interop.cs
public static unsafe class Interop
{
    internal static NativeApi* Native;

    [UnmanagedCallersOnly]
    public static int Initialize(NativeApi* native, ManagedApi* managed)
    {
        Native = native;
        managed->CreateInstance = &CreateInstance;       // static methods marked [UnmanagedCallersOnly]
        managed->InvokeUpdate = &InvokeUpdate;
        // ...
        return 0;
    }

    [UnmanagedCallersOnly]
    static void InvokeUpdate(IntPtr instance, float dt)
    {
        var entity = (Entity)GCHandle.FromIntPtr(instance).Target!;
        try { entity.OnUpdate(dt); }
        catch (Exception e) { Log.Error($"{entity.GetType().Name}.OnUpdate: {e}"); }   // never let an exception cross into C++
    }
}
Exceptions must stop at the boundary An exception that leaves an [UnmanagedCallersOnly] method terminates the process. Every entry point catches, logs to the editor's console with the script's name and line, and returns. In the editor, an exception in Play also pauses the game, so the error is easy to see.

4.4 The C# API

The API is what your son will read and write every day, so it is designed for clarity first. Vectors use System.Numerics.Vector3 and Quaternion (standard, SIMD, documented everywhere), not engine-specific math types.

// RollABall/Scripts/PlayerBall.cs: the first script of milestone 1
using System.Numerics;
using Morava;

public class PlayerBall : Entity
{
    public float Force = 12.0f;          // shown and edited in the Inspector, saved in the scene
    public Prefab? PickupEffect;

    Rigidbody body = null!;
    int score;

    protected override void OnCreate() => body = GetComponent<Rigidbody>();

    protected override void OnFixedUpdate(float dt)
    {
        Vector2 move = Input.GetAxis2D("Move");
        body.AddForce(new Vector3(move.X, 0, -move.Y) * Force);
    }

    protected override void OnTriggerEnter(Entity other)
    {
        if (!other.HasTag("Pickup")) return;
        score++;
        Log.Info($"Score: {score}");
        if (PickupEffect != null) Scene.Instantiate(PickupEffect, other.Translation);
        other.Destroy();
    }
}

4.6 Hot reload

Morava.ScriptCore stays loaded for the whole session. The game assembly is loaded by ScriptCore into a collectible AssemblyLoadContext, from a byte array (so the DLL file is not locked and dotnet build can overwrite it). Its Load override returns ScriptCore's own assembly for Morava.ScriptCore, so both sides agree on the Entity type.

When the editor (in Edit mode only) sees a newer DLL: destroy all instances, unload the context, wait until it's collected, load the new bytes, refresh the field lists. A reload in Play is refused with a message; Stop first.

What keeps an old assembly alive Any reference from ScriptCore or from C++ into the game assembly: a cached Type, a delegate, a GCHandle not freed, a static event subscription. If the context doesn't unload, the editor logs it: a WeakReference to the context that stays alive after a few GC cycles shows the leak.
As built: 4.6, hot reload
  • The watcher (src/Editor/EditorScriptReload.cpp, called each frame after Play mode's update). Every 250 ms it reads the project's script assembly's write time and size; a build that differs from the loaded one is loaded once both have stayed the same for 0.5 s (dotnet build writes the DLL, then the PDB). The reload is GameSystems::LoadScripts, as at project open: unload (C# drops its context and runs up to 10 GC cycles), then the new bytes, then the class and field lists. In the test project a reload takes about 70 ms; the log says Scripts: reloaded in 69 ms, a notification gives the class count. The first build of a project whose DLL didn't exist yet is loaded the same way. The player doesn't watch: a shipped game's scripts don't change.
  • During Play: at Stop, not refused. The plan refused a reload in Play; instead the game keeps the scripts it started with, the log and a notification say once that the scripts were rebuilt, and the reload happens when Play stops (Pause counts as Play). Building while playing is common, and nothing has to be done again afterwards.
  • The scene's values survive without any work: a ScriptComponent keeps its class by name and only the fields it sets (4.5), so a new field shows with its initializer, a removed one stays in the scene with the usual warning, and a renamed class is reported at Play as before.
  • Leaks. When the old context is still alive after the GC cycles, ScriptHost logs what can hold it (a static, a delegate or a GCHandle into the game), counts it (GetLeakedAssemblyCount) and the notification says the old scripts are still held; the new ones load anyway. ScriptHost::GetGameAssemblyWriteTime is the loaded file's write time, read before its bytes.
  • A build that fails to load (a broken DLL, a missing reference) is reported once and tried again only when there is a newer one. Project panel: Reload, next to Script Assembly, loads the scripts again now (not in Play); the missing-DLL warning now says the editor loads the scripts once they are built.
  • Checked with the scratch test project: an open editor, three dotnet builds 12 s apart: a class added (5 → 6 classes), one added whose static constructor subscribes to AppDomain.ProcessExit (7 classes), and the original again (5): the third unload reported the planted leak, each reload took 65-70 ms, about 3 s after the build started. 6.1 Prefabs

A prefab (.mprefab) is an entity subtree saved with the scene serializer. Instantiating it creates new entity IDs and remaps every entity reference inside the subtree (script fields of type Entity, parent links). In the editor: drag an entity to the content browser to make a prefab, drag a prefab into the scene to place it. Instances remember their prefab's UUID; "Apply to prefab" and "Revert" are the basic tools. Per-field override tracking (as in Unity) is Phase 10.

As built: 6.1, prefabs

6.4 The animator

struct AnimatorComponent
{
    AssetHandle Controller;        // .manim: states (clip, speed, loop) and transitions (condition, crossfade seconds)
    std::unordered_map<std::string, AnimatorParameter> Parameters;   // float, bool, trigger: set from C#
    AnimatorRuntime Runtime;       // current state, time, previous state and fade progress
};

The animation system samples the current state's clip and, while a transition runs, the previous one, blending each bone (lerp for translation and scale, slerp for rotation) by the fade progress. The bone matrices go to the skinning path the renderer already has (and to compute skinning for ray tracing). Example: Idle → Run when Speed > 0.1, Any → Jump on the Jump trigger, 0.15 s fades. Root motion and blend trees are Phase 10.

Two clips at once ModelH2M plays one clip per model today. The animator needs "sample clip A at time t into a pose" separate from "upload a pose", so two poses can be blended. That refactor is the main engine work of this step.
As built: 6.4, the animator (after 6.5, at the user's choice)
  • Two clips at once (src/Animation/AnimationClip, in the core): the skeleton is the model file's node tree, flattened with each parent before its children (AnimationSkeleton: bind matrices, which node gives which bone, the bone offsets, the inverse root transform); a clip (AnimationClip) keys nodes by name, in seconds; a pose is translation, rotation and scale per node. AnimationSampling::SampleClip (keys found by binary search; looped: wrapped, else held at its ends), BlendPoses (lerp, and slerp the short way), ComputeBoneTransforms (the matrices the skinning shaders and the ray tracing's compute skinning already read). ModelH2M plays its own clip through the same code now (its ReadNodeHierarchy and the interpolation functions are gone), and takes a pose from outside: SetPose until ReleasePose, during which its OnUpdate leaves the bones alone.
  • Clips from other files. Because channels bind to nodes by name, a clip of another file of the same rig drives the skeleton: the sample's character is Models/PirateVoid, three Mixamo exports (walking.dae with the mesh and a walk, idle.dae and using0.dae clips alone). AnimationClipLibrary reads each file once (only its clips are kept). In Place, per state: the clip's root channel (the animated node nearest the root: the hips) keeps its first key's place across the ground, its height still moving; Mixamo's walk moves the hips 1.5 m forward per cycle, which would snap back at each loop. Moving the entity by the clip (root motion) stays Phase 10.
  • The controller (AnimatorController, a .manim YAML file): parameters (Float, Bool, Trigger, with defaults), states (a clip: its file, empty for the model's own, and its name, empty for the first; speed, optionally times a Float parameter so a walk keeps pace with the character; loop; In Place), transitions (from a state or from Any State, to a state, fade seconds, an optional exit time, conditions that all have to hold: Float greater or less, Bool true or false, Trigger set). States and parameters are named and transitions name them, so an edit keeps the rest. AnimatorControllerLibrary keeps one object per file, shared by the editor and the running game.
  • The runtime (SceneAnimation, owned by GameSystems as physics and sound are; the guide's AnimatorRuntime isn't in the component, as 3.3 decided for physics): each frame after the scripts' OnUpdate (in Simulate too, in the entry states), the clips move on by the frame's time, then the first transition that may be taken is (Any State's first, then the current state's; Any State doesn't start the state it is in again; the triggers it tested are used up), the current state is sampled and, while a crossfade runs, blended over the state it came from, which goes on playing. A crossfade started during another fades from the pose shown then (a snapshot), so nothing jumps. An edited controller is taken at the next frame, states and parameter values kept by name. Stop gives the models back their own playback. Spawned prefabs get their animators (AddEntities, 6.2). The editor runs one more outside the game: in edit mode the scene's animators show their entry states, as the game starts them (Sync each frame takes in an Animator added, removed, or given another controller or model), and Play hands the models to the game's.
  • The component: AnimatorComponent { Controller } on the model's entity, Animator: {Controller: Assets/Animators/Character.manim} in the scene file (a path until Phase 8's asset handles). The parameters live in the controller, their values in the runtime.
  • C#: Animator (GetComponent<Animator>()): SetFloat, SetBool, SetTrigger, ResetTrigger, GetFloat, GetBool, Play(state, fade), CurrentState, StateTime, NormalizedTime, IsInTransition, TransitionProgress. A name the controller doesn't have (or of another type) throws ArgumentException.
  • Editor: the Inspector's Animator section on skinned models (the controller: dropped, chosen, or New: a state for each of the model's clips in Assets/Animators; while the game runs, the animator's debug view: the state, its time, the crossfade with a progress bar, the transitions taken, and the parameters, which can be set there as a script would). 6.5 Frustum culling for the main view

Only the shadow and water passes cull today. With spawned objects, the main view needs it too: each mesh part's world bounding box against the six frustum planes, before the G-buffer prepass and the scene pass. The profiler shows drawn versus culled counts.

Debug views Bounding boxes of culled parts (with a frozen-camera toggle to look at the frustum from outside), animator state and fade progress on the selected entity, prefab instance markers in the hierarchy.
Check Spawn 500 pickups from a prefab: frame time stays flat when they are off-screen; a character crossfades between idle, run and jump without pops; a script loads a second level and back.
As built: 6.5, frustum culling (before 6.4, at the user's choice)
  • What culled before: less than the text above says. The shadow passes of spot and point lights skipped models out of the light's range, the probes skipped boxes outside a cube face; the sun's cascades and the water drew everything.
  • The main view (CullMainView, EnvMapVulkanRenderer): after the water reflection, before the G-buffer prepass, each mesh's box, turned with the mesh into the world (center moved, half size along the world axes from the absolute matrix), against the six planes of the camera's view-projection (Gribb and Hartmann). A box is culled only when it is entirely behind one plane: conservative, a few boxes across the frustum's corners are drawn unseen. The result is a flag per mesh in the frame's mesh order (the order of the motion vectors' previous transforms), read by the prepass, the scene pass and the glass; a model with no mesh in view binds nothing. Skinned meshes are never culled: their bones move them out of their boxes (the probes made the same choice).
  • The shadow maps too: DrawShadowCasters tests each model's world box against the view-projection of the pass it draws into, for the sun's cascades as for spot and point lights. That drops only what the rasterizer would have clipped: a cascade reaches back towards the sun behind every caster, so a model behind the camera still casts into the view. Before, every caster was drawn into each of the four cascades.
  • Not culled: the water's planar reflection (a mirrored camera; it can get its own frustum later) and ray tracing (every instance in the top-level structure: reflections and GI see what the camera doesn't).
  • Profiler and debug views (Renderer Stats panel, Scene section): "Main view: N of M meshes drawn, K culled", and toggles in the view options (not saved): Frustum Culling (off draws everything, shadows included), Freeze (keeps the view-projection culled against while the camera moves) and Show Culled (red boxes of the culled meshes, the frozen frustum in yellow, as lines in the editor overlay). The prefab instance markers were already in the hierarchy (6.1); the animator's debug view comes with 6.4.
  • Found on the way: the Editor Overlay pass walked every model's parts each frame for the selection, also in the player, where it draws nothing (4.9 ms with 500 crates in Debug); it now walks the scene only when there is a selection or an overlay that draws models.

7.5 Cameras that draw into a texture

A rear-view mirror, a minimap, a security monitor, a portrait in a menu: a game camera (6.3) whose view is drawn into a texture instead of the screen, and the texture shown on a mesh (a material's map) or by a UI image (7.1).   • CameraComponent gets a Target: none (the screen: the primary camera, as in 6.3) or a render texture, an asset with a size and a format (.mrtex; the same handle a material's map or a UI image takes). 8Assets and cooking

Goal: every asset has a UUID, scenes reference UUIDs, a cooker converts source assets into runtime formats, and the player reads one pack file. After this phase the player links neither assimp nor shaderc.

8.1 The asset registry

Each source file gets a sidecar .meta file with its UUID, type and import settings (texture: sRGB or linear, normal map, compression; model: scale, which animations). Sidecars survive moving files in Explorer or Finder together with their asset, and merge cleanly in Git. The registry scans the asset folder at startup and watches it for changes. Scenes already reference materials by ID; models, textures, HDR maps, sounds, fonts and prefabs follow. The serializer reads old path-based scenes and writes UUIDs, so existing scenes migrate by opening and saving them.

Together with moving assets out of the repository The deferred plan to move 678 MB of third-party models and textures out of Git fits here: once scenes reference UUIDs, the sample assets can live in a separate download or repository with their .meta files, and nothing in the engine refers to their paths.
Shared models: load a file once Today every entity with a model loads its file again: the sample's Physics scene has 123 models (nearly all cube.obj) and takes about 8 s to open in Debug (measured 2026-10-23, in 4.5). Each load is an assimp import with its own vertex and index buffers, because each model entity owns its ModelH2M (its parts' transforms are written into that model's meshes). Two changes, in this order:
  • Trim the load first (small, independent): ModelH2M creates a Hazel material per mesh, with a reflection of HazelPBR_Static.glsl and its descriptor sets and uniform buffers, which the Vulkan renderer doesn't use (its materials are EnvMapVulkanMaterial): 246 reflections for that scene. The load also logs about 27,000 lines (descriptor sets, "No normal map", buffer allocations), which cost time in Debug. Make neither for this renderer's models, and keep the log to one line per model file.
  • Then share the geometry. The registry loads a model asset once (by its UUID) and every entity using it refers to the same vertex and index buffers, skeleton and animation clips. What differs per entity moves out of the shared model: the parts' transforms (into MeshPartComponent, given to the renderer per draw instead of written into the mesh), the parts' materials (already per part), and a skinned model's animation state and bone matrices. Ray tracing then builds one bottom-level structure per model asset, and the top-level structure has an instance per entity. Opening a scene costs a load per distinct file, not per entity; with cooked meshes (8.2), a read and an upload.

  • Player settings (resolution, fullscreen, VSync, quality, volumes, key bindings) saved in the user's folder, edited by the game's settings menu.
  • Save data for scripts: a small key/value file (SaveData.SetInt("Level", 2)) in the same folder.

11Editing a model's meshes

Goal: a model entity's meshes can be changed in the editor without making the entity again: its model file replaced by another (the sample's cube Player becomes a sphere, keeping its transform, character, script, tags and the fields set in the scene), and meshes from another file added to it or removed from it. Asked for by the user on 2026-10-23, as the last phase.

Today

A model entity has a ModelComponent (the file's path, and its own loaded ModelH2M) and a child entity per mesh with a MeshPartComponent: the mesh's index in the file (SourceMeshIndex, which a saved scene matches parts by), its material and its transform in the model. A part can be removed, but every part belongs to the model's one file: nothing changes the file, and nothing adds a part from another one. Replacing a model today means a new entity and every component made again by hand.

Why after Phase 8 Phase 8.1 (Shared models) changes what a part is: the geometry is loaded once per asset and referenced by UUID, and a part's transform and material are the entity's, given to the renderer per draw. With that, a part can name its own asset (Asset UUID plus SourceMeshIndex), so a model can be made of meshes from several files, and replacing a model is changing a UUID rather than reloading a ModelH2M that owns its parts' state. Built on today's model, both would have to be rebuilt after 8.1.

11.1 Replace the model

  • Inspector, Model: the file, with Replace… (the asset's file dialog) and a drop target for a model dragged from the Content Browser. A Primitive menu next to it offers the engine's Models/Primitives (cube, sphere, capsule, cylinder, cone, quad) without a dialog.
  • What stays: the entity and its ID (other entities' script fields that name it still work), its transform, name, tags, script and its fields, character, rigid body, and every other component. What changes: the parts. A new file's mesh whose name (else its index) matches an old part keeps that part's material and transform; the others get the file's own.
  • Physics: a box, sphere or capsule collider is offered a refit to the new model (Fit to Model, as now); a convex or triangle mesh collider follows the new meshes by itself. A character keeps its capsule: its sizes are in meters, chosen for the game, not the model.
  • Not during Play, as for other structural edits (Save and part removal are refused there too).

11.2 Add and remove meshes

  • Add Mesh… on a model (Inspector, or the Scene Hierarchy's menu on the model) picks a file and one or all of its meshes; each becomes a new part under the model, with its own asset, index, material and transform. A mesh can also be dropped from the Content Browser onto a model in the Scene Hierarchy.
  • Remove on a part, as now; a model may end up with no parts (an empty model: a placeholder that a script fills).
  • Saved in the .mscene: a part that comes from another file than its model's has its own Asset; parts of the model's file are written as now, so older scenes read unchanged.
  • Ray tracing and probes: the model's top-level instances follow its parts (one per part's asset, sharing the bottom-level structures of 8.1), and the change counts as a geometry change for the probes, as adding a model does now.

11.3 With prefabs

In a prefab (6.1) the change is made in the prefab and reaches its instances. On one instance it is an override, which needs the prefab overrides of Phase 10; until then, the editor asks to unpack the instance first.

Checklist before calling it a game engine

  • A new project, a scene, a C# script and a Build Game, done by someone who only read the project's README, in under an hour.
  • Play/Stop 50 times: no growth in memory, bodies, sounds or managed objects (the debug panels show the counts).
  • All CI jobs green, including the exported-player smoke tests on Windows, Linux and macOS.
  • Every debug view of this guide reachable from the editor.

Common mistakes

  • Gameplay code in OnUpdate that moves physics bodies: jitter and frame-rate-dependent behavior. Forces and character movement go in OnFixedUpdate.
  • Setting a dynamic body's transform every frame from a script: it fights the solver. Use forces, velocities, or make it kinematic.
  • Calling scripts from a Jolt contact callback: data races. Queue, then dispatch.
  • Destroying an entity while iterating: deferred destruction only.
  • A C# exception crossing into C++: the process ends. Catch at every entry point.
  • A static field in a game script that holds a reference to an engine object across reloads: the old assembly can't unload.
  • Loading a file by a path relative to the working directory in the player: works on your machine, fails on the customer's.
  • Shipping a build with the validation layer enabled or with AVX2-only code: works on your machine, fails on the customer's.
