MoravaEngine · a platform for the player

Android Export

The plan for building a MoravaEngine game as an Android app: MoravaPlayer, the Vulkan renderer and the game's C# scripts running natively on a phone, built from the editor's Build Game like the Windows, Linux and macOS games. It is laid out so that an iOS export later is mostly a new platform backend, not a second port.

Drafted November 7, 2026, from the code on master. Names that exist in the code are written as they are. Names of new classes, files, folders and settings are proposals. Decisions marked default were left open and can be changed before their phase starts.

The decisions

  • The player stays C++. Android runs the same MoravaCore and PlayerLayer, started from a GameActivity (Android Game Development Kit) instead of GLFW. There is no Java or Kotlin game code. A small MoravaActivity subclass only loads the native libraries and sets fullscreen.
  • Vulkan only. OpenGL, DirectX 11, the older scenes, the editor, ImGui and the legacy Mono code aren't built for Android.
  • C# scripts: NativeAOT (default). ScriptCore and the game's scripts are compiled per game into one native library, libMoravaGame.so. hostfxr and loading a .dll at runtime aren't available on Android or iOS. NativeAOT is the path iOS will need too, and the engine's interop is already a table of blittable C function pointers (NativeApi), which NativeAOT handles well. Phase 0 checks it before anything depends on it. The fallback is an embedded Mono runtime (Risks).
  • hostfxr stays in the editor. It gives hot reload (GameLoadContext), normal C# debugging and the Inspector's reflection over a freshly built .dll. Whether shipped desktop games also switch to NativeAOT is decided after Phase 3. The main cost is that a Windows editor could no longer build a Linux game's scripts without WSL or CI, which GameBuilder::CanBuildFor allows today.
  • Textures: BC on the desktop, ASTC on mobile. NVIDIA and AMD desktop GPUs have no ASTC, and Intel Macs have no ASTC, so BC5 and BC7 stay for Windows, Linux and macOS. The cooker writes the format per target pack (Phase 4). Basis Universal (one pack for every platform) was considered and not chosen: lower quality and a conversion at every load.
  • The target: most Android devices in use today, not one phone. Google's distribution dashboard (handheld devices, November 2025) reports these shares:
    • no Vulkan: 7.4%
    • Vulkan 1.0: 3.9%
    • Vulkan 1.1: 62.1%
    • Vulkan 1.3: 26.0%
    • Vulkan 1.4: 0.7%
    Android reports no 1.2 level, so today's Vulkan 1.2 requirement is only guaranteed on about 27% of phones.
  • Vulkan 1.1 is the Android minimum. With ray tracing off, the renderer appears to need little from Vulkan 1.2 beyond how its shaders are compiled, and Phase 0 confirms it. 1.1 reaches about 89% of phones. Ray tracing, and the features it turns on, stay above that line on every platform.
  • A device matrix, not a test phone. One phone per GPU family the market uses: Arm Mali, Qualcomm Adreno, and a budget PowerVR (Imagination) or older Mali. Each at the low end of what is common, plus one recent mid-range phone. The Redmi Note 13 Pro (Helio G99-Ultra, Mali-G57 MC2, 2400×1080) is the Mali at hand. The others are borrowed or run in a cloud device lab (Firebase Test Lab). Success means 30 fps at the lowest tier on the low-end phones, not on the Redmi alone.
  • 30 fps is the default frame cap on Android. Both orientations are supported, following the phone's sensor unless a project locks one. Package names start with com.dtrajko. Play Store publishing waits until it is needed (Phase 7).
  • ABI and versions: arm64-v8a only (plus x86_64 for the emulator if it proves useful), and minSdk 29 (Android 10). Android 10 is also the version from which new 64-bit devices must have Vulkan 1.1, and Android 9 and older are a few percent of active devices. Phones with only 32-bit ARM, mostly low-cost Android Go phones, are left out, a small and shrinking share. A phone that fails VulkanSupport::ChooseDevice gets its message as an Android dialog.
  • Input (default): all three, in this order: gamepad (free through the existing action system), a raw touch API for C#, then engine on-screen controls (a virtual stick and buttons) mapped to .minput actions.
  • Output (default): a debug-signed APK built from the Windows editor first (and from the Linux editor, which shares the code). A signed Play Store AAB comes last, in Phase 7.
  • No Gradle on the game maker's machine. CI builds an Android player template with Gradle, the same way it builds the other platforms' templates (cmake/PlayerTemplate.cmake, Tools/Get-PlayerTemplates.ps1). The editor assembles the APK from it with the Android SDK's command-line tools: aapt2, zipalign and apksigner.
  • iOS isn't built yet: there is no Mac and no Apple Developer Program membership ($99 a year). Every phase still puts platform code behind the seams of Phase 1, so iOS later is a backend. The existing macos.yml workflow also shows that iOS can be compile-checked on GitHub's macOS runners without owning a Mac.

What blocks Android today

A survey of master. Most of the engine (Jolt, miniaudio, entt, yaml-cpp, the Vulkan renderer, packs) is portable C++. The problems are a handful of seams where the desktop leaks in.

The shape of the port

The work splits into one layer of seams (Phase 1) and one backend per platform behind it. Everything above the seams is shared by desktop, Android and later iOS.

Phase 0: spikes de-risk

Three small experiments, each on a throwaway branch, before the engine is changed. Their results are written into this page in an "As found" box.

  • NativeAOT on Android.
    • Publish ScriptCore plus Projects/Sample/Scripts as one shared library: PublishAot, NativeLib=Shared, RuntimeIdentifier=linux-bionic-arm64, linked with NDK r27 or newer. Uno Platform's documentation reports NativeAOT Android apps on .NET 10 with NDK r27+ and an experimental-status warning (XA1040).
    • Find out whether a Windows machine can produce it. NativeAOT generally doesn't compile across operating systems; if Windows can't, the step runs in WSL2 (already used for the Linux builds) or through the .NET for Android workload's toolchain.
    • Load it from a minimal NDK app, call an [UnmanagedCallersOnly(EntryPoint = "morava_script_init")] export that returns the Interop table, and call one function in each direction.
    • Check that Activator.CreateInstance, GetTypes() and the script-field reflection work with the game assembly rooted (TrimmerRootAssembly). Record the size of the .so.
  • What the renderer needs below ray tracing. On the desktop, with --no-ray-tracing, list every shader the Mobile and Low tiers load, every extension and feature the device is created with, and every Vulkan 1.2 call. The result is the engine's Android feature list. It is checked against the Vulkan 1.1 Android Baseline profile and against the gpuinfo.org reports of common phone GPUs: Mali-G52, Mali-G57, Adreno 610, Adreno 618 and PowerVR GE8320. Anything that phones commonly lack becomes optional or gets a fallback in Phase 1.
  • The phones at hand. vulkaninfo (or the Khronos hardware capability viewer) on the Redmi Note 13 Pro and any phone you can borrow records:
    • the Vulkan version and whether the 1.2 core features are reported
    • textureCompressionASTC_LDR, max image size, memory heaps
    • the core features VulkanContextH2M turns on without checking: fillModeNonSolid (wireframe) and samplerAnisotropy. If a phone lacks either one, device creation fails, so Phase 1 makes them conditional.
    Then check which of the 28 nonuniformEXT shaders the renderer loads with ray tracing off; any that load without descriptor indexing enabled is a bug on desktop GPUs too.
  • ASTC encoding. Build Arm's astc-encoder (Apache 2.0) into the cooking tools. Time it on Sample's textures at 6×6 and 4×4, and compare quality with the BC7 output.
Done wheneach spike has a yes or no, a number (library size, cook time) and the chosen route written here. A "no" on NativeAOT switches Phase 3 to the Mono route before Phase 1 starts.

Phase 1: platform seams, on the desktop engine

The whole of this phase is done and tested on Windows and Linux. Nothing Android-specific is added yet, so CI's existing smoke tests prove nothing broke. This is the phase that makes iOS cheap later.

  • Clock: Core/Timer.cpp uses std::chrono::steady_clock instead of glfwGetTime.
  • Window: Application.cpp gets the framebuffer size from Window. Monitor and video-mode code in PlayerLayer.cpp and EnvMapVulkanRenderer.cpp moves behind Window (GetDisplayModes, SetFullscreen), and a mobile window reports one mode.
  • Vulkan surface: a VulkanSurfaceProvider gives VulkanContextH2M its instance extensions and gives VulkanSwapChainH2M its surface. The GLFW implementation keeps today's calls.
  • Vulkan 1.1 when ray tracing isn't used:
    • VulkanSupport::ChooseDevice accepts a Vulkan 1.1 device and turns ray tracing off on it
    • the instance and device are created with the lower of the device's version and 1.2
    • ShaderCompile compiles shaders for Vulkan 1.1 (SPIR-V 1.3), and for Vulkan 1.2 only those that need 1.2 (the ray-traced ones)
    • the pack stores both forms where they differ
    • on the desktop, tested by forcing the 1.1 path with a command-line switch
  • Optional device features: VulkanContextH2M turns on fillModeNonSolid and samplerAnisotropy only when the device reports them, as it already does for wideLines. Without wireframe support, the wireframe debug view is hidden.
  • Swapchain lifetime: the swapchain can be destroyed and recreated around a lost surface. On the desktop this is tested by minimizing and restoring, and with a debug key that forces it.
  • Input: InputSystem reads keys, buttons, axes and gamepads from an InputBackend. The GLFW backend wraps today's polling. Touch is part of the interface from the start (empty on the desktop) so the C# API in Phase 3 has a single source.
  • Files: one place answers where the pack is (OpenPackStream()) and where writable data goes (GetWritableFolder()). GameSettings.cpp, StoredValues and save data use it.
  • Lifecycle: AppLifecycle events (Pause, Resume, SurfaceLost, SurfaceCreated, LowMemory) reach Application. Pause stops game time and audio. On the desktop they come from focus and minimize.
  • Script host: ScriptHost is split into an interface with two backends. ScriptHostHostfxr is today's code. ScriptHostAot loads a library and calls morava_script_init, and it runs on the desktop too, against a NativeAOT build of Sample's scripts (win-x64 or linux-x64). Running the AOT path on the desktop first means scripts are known to work before a phone is involved.
  • C#: Interop.cs gets the exported entry point. The hot-reload GameLoadContext stays, but only the hostfxr build uses it (#if !MORAVA_AOT).
Done whenthe Windows and Linux CI jobs pass unchanged, Sample plays in the editor and in MoravaPlayer, and MoravaPlayer also plays Sample with its scripts from a desktop NativeAOT library.

Phase 2: the first frame on a phone engine android

  • CMake: cmake/Android.cmake, chosen when CMAKE_SYSTEM_NAME is Android (the NDK's android.toolchain.cmake, ABI arm64-v8a, platform android-29, c++_shared). It forces MORAVA_VULKAN on and OpenGL, DX11 and MORAVA_MONO off. It builds only MoravaCore and the player, the player as libMoravaPlayer.so instead of an executable, without shaderc. Native libraries are linked with -Wl,-z,max-page-size=16384 for 16 KB page devices.
  • Platforms/Android: a Gradle project that depends on androidx.games:games-activity and calls the CMake build through externalNativeBuild. It is used by CI to make the template and by you for debugging in Android Studio. The manifest asks for the sensor's orientation (fullSensor, with orientation and screen-size changes handled by the app instead of restarting it), fullscreen and the Vulkan feature (android.hardware.vulkan.version 1.1, 0x401000), so stores hide the game from phones without it.
  • AndroidMain.cpp: GameActivity's android_main drives Application's loop, handles APP_CMD_INIT_WINDOW and APP_CMD_TERM_WINDOW through the Phase 1 lifecycle, and passes command-line style arguments from the launch intent (--scene, --exit-after-seconds) so tests can drive it.
  • Surface: VK_KHR_android_surface. Pre-rotation: the swapchain uses the surface's currentTransform, and the projection is rotated to match, so the compositor doesn't rotate every frame.
  • Logging: spdlog's android_sink, so MORAVA_CORE_* and H2M_* appear in logcat under the tag Morava.
  • Pack: Game.mpak is stored uncompressed in the APK's assets/. AndroidFiles opens it with AAsset_openFileDescriptor64 and gives AssetPack::Open a stream reading from that descriptor and offset. Nothing is copied out, and the pack format doesn't change.
  • Textures for now: a PackBuilder option that stores textures uncompressed (RGBA8), so the first frame doesn't wait for Phase 4.
  • Quality: start at Low, with ray tracing off (the device has none, or --no-ray-tracing).
  • Validation: Debug builds package the Khronos validation layer, so its messages show up in logcat.
Done whenSample's start scene renders on the Redmi Note 13 Pro and on one Adreno phone (borrowed or in the device lab) without scripts, rotates and survives Home and back without a crash, with no validation messages. Frame time is noted for Phase 4.

Phase 3: scripts and input engine android

  • Scripts: ScriptHostAot on Android loads libMoravaGame.so with dlopen (it sits beside libMoravaPlayer.so in lib/arm64-v8a). For now it is built by hand with the Phase 0 command. The engine side doesn't change: the same ScriptNativeApi table, the same InvokeMethod entries.
  • Gamepad: GameActivity's key and motion events go into AndroidInput, mapped to the same gamepad buttons and axes the GLFW backend reports. The existing .minput bindings work unchanged.
  • Back button: reported as the Escape key and the gamepad's Start, so the games' existing Pause bindings open the pause menu. A Back press in the main menu asks to quit.
  • Touch for C#: new entries appended at the end of ScriptNativeApi and NativeApi, in the same order (Input_GetTouchCount, Input_GetTouch). In ScriptCore/Input.cs:
    • Input.TouchCount and Input.GetTouch(int), returning a Touch with Id, Phase (Began, Moved, Stationary, Ended, Canceled), Position and Delta in pixels
    • Application.IsMobile, so a script can show touch hints instead of key names
    The desktop reports no touches, except in an optional "mouse as touch" mode for testing in the editor.
  • UI: a touch on a UI button counts as a click, so the menus work with a finger.
Done whenCoin Collector plays on the phone with a Bluetooth gamepad, its menus work by touch, and a test script logs touches with their phases.

Phase 4: mobile textures and rendering engine

  • Packs per platform: PackBuilder gets a target platform. Desktop packs keep BC7 and BC5; Android packs get ASTC. The cooked-texture cache is kept per format.
  • ASTC formats (to confirm in Phase 0): color maps 6×6 sRGB, other maps 6×6, normal maps 4×4 with the two-channel encoding. A device without textureCompressionASTC_LDR gets textures decoded to RGBA8 at load, slower but correct.
  • Mobile quality tiers: phones range far more widely than desktop GPUs, so there are two tiers below Low, decided after measuring:
    • Mobile: no ray tracing, probe GI updates or path tracer; smaller shadow maps, half-resolution GTAO, a cheaper bloom, a render scale around 0.75
    • Mobile Low: no GTAO, one shadow-casting light, a render scale around 0.5
    Both scale up to the screen. On Android, QualityTier chooses between them from the GPU family, its core count, the device's memory and a two-second benchmark at the first start, kept until the player changes it in Settings.
  • Tile-based GPUs: check every render pass's load and store operations (clear or don't-care instead of load where possible). Use lazily allocated, transient attachments for depth and G-buffer targets that aren't read later. Remove copies between full-screen passes where they can be merged. Android GPU Inspector or RenderDoc shows where bandwidth goes.
  • Frame pacing: a frame cap (30 or 60, a setting) with FIFO presentation. Android's frame pacing library (Swappy) is added only if the cap alone stutters.
  • Memory: respond to the LowMemory lifecycle event by dropping cached, unused assets. Record peak memory on each phone, and keep it within what a 3 GB phone allows an app.
The low end decides the rendererThe common phone GPUs are small: two to four cores (Mali-G52, Mali-G57, Adreno 610), often on 3–4 GB of RAM and screens of 2400×1080 or more. A deferred G-buffer, GTAO and bloom leave them little to spare. If Phase 2's frame times on the low-end phones are far from 33 ms even at a render scale of 0.5, a forward path for Mobile Low moves from "Risks" into this phase.
Done whenCoin Collector runs at 30 fps for 15 minutes on every phone in the matrix at the tier QualityTier picks for it, without thermal throttling bringing it under 25 fps. The APK size, peak memory and the tier and render scale each phone got are written here.

Phase 5: touch controls and the app's life engine game

  • On-screen controls: a TouchControlsComponent (UI), shown only when Application.IsMobile and no gamepad is in use. Its parts:
    • a virtual stick that drives a 2D action (move)
    • a look area (drag on the right half) that drives a 2D action (look)
    • buttons, each bound to a button action (jump, interact, pause)
    The bindings go in the project's .minput, so a script reads Input.GetAction("Move") whatever the device. The Inspector edits their placement and size.
  • Safe area: a Screen.SafeArea for C#, and UI anchors that keep controls out of camera cutouts and gesture bars.
  • Orientation: a project setting: Any (following the sensor, the default), Landscape or Portrait. A rotation changes the swapchain and the camera's aspect ratio, and the UI's anchors place the touch controls for each orientation. Every test scene is checked in both.
  • Pause and resume: game time, physics and audio pause when the app goes to the background. The swapchain is recreated on return, and settings and save data are written on pause, because Android may kill a paused app without warning.
  • Audio: miniaudio's AAudio backend, paused and resumed with the app.
  • Keep the screen on while a game is playing.
Done whenCoin Collector plays by touch alone, and 20 cycles of Home, back, rotate and screen-off/on run without a crash, a leak (memory after cycle 20 within a few percent of cycle 1) or a validation message.

Phase 6: Build Game for Android editor

  • CI template: a new Android job in .github/workflows/build.yml (Ubuntu, the NDK, the Android SDK, a JDK) builds Platforms/Android in Release. It uploads the player template PlayerTemplates/android-arm64: libMoravaPlayer.so, libc++_shared.so, the compiled classes.dex of MoravaActivity and GameActivity, a manifest template, resources and the license notices. Tools/Get-PlayerTemplates.ps1 fetches it like the others.
  • GameBuilder: android-arm64 appears in GetPlatforms() when the template and the tools are found. FindAndroidSdk() looks in ANDROID_HOME, then Android Studio's default folder, and a missing tool is named in the log. The build steps:
    1. cook the Android pack (ASTC textures)
    2. publish the game's scripts with NativeAOT into libMoravaGame.so (from ScriptCore/Aot/MoravaGameAot.csproj.in; in WSL if Phase 0 says so)
    3. fill in the manifest (package name, version, app name, orientation) and link it with the icon using aapt2
    4. zip the template, the pack (stored uncompressed), and the libraries; then zipalign and apksigner
  • Signing: a debug keystore is created on first use in the user's folder, as Android Studio does.
  • Project settings (an Android block in the .mproject, shown in the editor's Project Settings): PackageName (for example com.dtrajko.coincollector), VersionCode, VersionName, Orientation, an icon, DefaultQuality.
  • Build and Run: when adb sees a phone, the editor installs and starts the game and streams its logcat into the editor's log.
  • Command line: --build-game <project> --platform android-arm64, as for the other platforms, for CI and the tests.
Done whena fresh Windows machine with the editor, the template, the Android SDK and the NDK builds Coin Collector into an APK from Build Game, and the APK installs and plays on the phone. The same command works from the Linux editor.

Phase 7: Play Store release editor

Not scheduled: done when a game is ready to publish.

  • A release keystore chosen in Project Settings. Its passwords aren't saved in the project.
  • An Android App Bundle (.aab): aapt2 link --proto-format and bundletool, beside the APK.
  • A check of Google Play's current requirements when this phase starts: the target API level, 16 KB page alignment of native libraries (already linked for it in Phase 2), and the data-safety form.
  • Optionally, Play Asset Delivery for packs larger than the base module's size limit.

Risks and open questions

  • NativeAOT on Android is still marked experimental by Microsoft (the XA1040 warning). If Phase 0 fails, or it breaks later: embed the Mono runtime from the .NET for Android packs, which allows JIT and runtime loading of the game's .dll on Android. That route needs no per-game native compile but uses more memory and starts more slowly. iOS would then use Mono's full AOT, which also needs a Mac.
  • Building NativeAOT for Android from Windows may not be possible. If so, the editor calls WSL for that step, or CI builds the scripts.
  • Driver variety. Android Vulkan drivers vary more than desktop ones, between vendors and between driver versions of the same GPU. Other projects report, for example, that the Mali-G57 lacks clip distances, which MoravaEngine's shaders don't use. The device matrix covers each GPU family, and logcat reports from the cloud device lab catch device-specific crashes before a game is shared.
  • Vulkan 1.1 may need more than shaders. If Phase 0 finds that the non-ray-traced path depends on a Vulkan 1.2 feature many phones lack, it gets a fallback in Phase 1. Otherwise the minimum stays at 1.2 and reaches fewer phones.
  • Phones without Vulkan (about 7% of handhelds) can't run the game. An OpenGL ES renderer isn't planned.
  • Deferred rendering costs bandwidth on tile-based GPUs. If Phase 4 can't reach the target, a forward path for Mobile Low becomes its own plan.
  • Emulator Vulkan may lack features the renderer needs. A real phone is the reference; the emulator is only for the lifecycle and input logic.
  • Package size: the runtime in the NativeAOT library plus the engine's .so. Measured in Phase 0 and Phase 4.

Left for the spikes

  • Whether NativeAOT on Android holds up (Phase 0). If not, Phase 3 takes the Mono route.
  • Whether Windows can build the Android script library, or that step goes through WSL.
  • The renderer's feature list below ray tracing, and whether Vulkan 1.1 is enough for it.
  • Which phones beyond the Redmi make up the device matrix.
  • The ASTC block sizes, from quality and cook time.
  • After Phase 3: whether shipped desktop games also switch to NativeAOT.

How each phase is checked

  • Desktop builds, for every phase:
    • Debug and Release, editor and player
    • the GCC check of the changed C++ files (Tools/Testing/gcc-check.sh)
    • dotnet build of ScriptCore and Sample's scripts
    • the existing CI smoke tests (player, animator, Erika, collector)
  • Android builds from Phase 2: the CI Android job builds the player and the template, and fails on new compiler warnings.
  • Setting up the Redmi: in Developer options, turn on USB debugging, "Install via USB" and "USB debugging (Security settings)". On HyperOS the last two need you signed in to a Xiaomi account, and without them adb install and input injection are refused.
  • On the phone (Tools/Testing/Run-Android.ps1): it installs the APK, starts it with --scene and --exit-after-seconds through the launch intent, and saves logcat to a file. The same checks as Run-Engine.ps1 then apply: no validation messages, no errors, the scene loaded, the scripts started.
  • Captures: adb exec-out screencap of each test scene, compared by eye with the desktop at the same quality.
  • The device matrix: from Phase 2, each Android build runs Sample's test scenes on every phone in the matrix, local or in the cloud device lab. A crash, a validation message or a black frame on any of them fails the phase.
  • Performance: the debug overlay's pass table at each mobile tier, plus frame times over 15 minutes from logcat, per phone.
  • You try each phase on the phone.
